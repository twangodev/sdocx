# Native canvas matrix expansion

Run `python3 tools/pencil2-canvas-matrix/check.py` to verify the shipped Graphics library identity, the two canvas vtable relocations, and selected ARM64 instructions and constant. This uses the existing checkout-local binary and binutils; it does not invoke the application.

`SPPenCanvas::GetCanvasMatrix` (RVA `0xae4e8`) and `SPPenCanvasRT::GetCanvasMatrix` (RVA `0xb0310`) make a virtual call at slot `0xd8`. The two recorded class vtables resolve that slot to their respective `GetModelMatrix` methods; a subclass override or dynamic symbol interposition can change the actual target. If that call returns the expected nine-float Matrix3, the subsequent stores expand it in storage order to `[m0,m1,0,m2, m3,m4,0,m5, 0,0,1,0, m6,m7,0,m8]`. Each passes that expansion and another matrix obtained through virtual calls to the helper at `0x93b08`. Manual disassembly of the helper shows multiply and accumulate instructions; the check verifies its call site, not the helper's semantics. This is static evidence of an available canvas conversion path. It does not establish that the synthetic Pencil2 list calls this method, identify the other matrix or prove normal page scheduling or device output.

The check pins the checkout-local `libSPenGraphics.so` by SHA-256. It does not independently establish the originating APK, package version, or device provenance. `readelf` is taken from the host PATH and the checkout-local cross-objdump and its dependent libraries are not pinned by this check; the complete library hash and reproducible disassembly bound the result to these bytes, not to a separately verified toolchain.

`python3 tools/pencil2-canvas-matrix/product-check.py` checks selected caller instruction presence and selected first-column SIMD instructions in address order; the product and caller dataflow below are a manual reading of the full disassembly. Reading the full helper's loads and stores as column-major 4×4 matrices, it computes `A × B`, where `A` is the 4×4 result of the preceding chained virtual calls and `B` is the expanded model matrix. In particular, the first output column starts with `A[:,1] * B[1,0]`, then adds `A[:,0] * B[0,0]`, `A[:,2] * B[2,0]`, and `A[:,3] * B[3,0]` using the observed multiply/add sequence. The SIMD operations use fused multiply-add, so a differently ordered scalar product need not be bit-identical. This is static analysis of this helper and two callers; the preceding virtual targets, real page execution and renderer handoff remain unverified. The check samples instruction patterns and caller wiring, rather than proving every load or alternative implementation; the same binary and toolchain qualifications above apply.

`python3 tools/pencil2-canvas-matrix/virtual-target-check.py` checks a concrete static route for a default `SPScreenBitmap` passed into `SPPenCanvas`. The canvas constructor passes its bitmap argument to `SPPenCanvasImpl`, which stores it at offset 8; `GetCanvasMatrix` retrieves it through the impl at canvas offset 32. For this screen bitmap, the first call at slot `0x98` resolves to `GetBitmapWritable`, returning the secondary interface at bitmap offset `0xb0`. The screen constructor installs the secondary vtable at that offset; its slot `0x10` resolves to the non-virtual thunk to `SPScreenBitmap::GetProjectionMatrix`, which adjusts the pointer back by `0xb0`. Therefore, for this concrete default class and intact constructor state, the other input to the helper is the screen bitmap projection matrix. This is a static resolution, not an observed call: alternate bitmap classes, overrides or symbol interposition can change it. The RT method has the same indirect call sequence, but this check does not establish its constructor or bitmap's target. The check also pins the vtable symbol value, the constructor GOT relocation, both slot relocation types and zero addends, and the address arithmetic tying those slots to the vtable. The selected instruction checks are not a full dataflow proof and retain the binary and toolchain limitations above.

`python3 tools/pencil2-canvas-matrix/screen-projection-check.py` checks selected instructions in the base bitmap constructor, identity matrix constructor and screen projection getter. The base constructor stores the four integer arguments after the queue as `(x, y, x + width, y + height)` at offsets 32–44. The screen getter reads the rectangle at offset 32 using imported `Rect::Width` and `Rect::Height`, and reads the screen constructor's final boolean at offset 204. It builds an identity matrix and overwrites column-major lanes 0, 5, 10, 12, 13, 14. For finite nonzero returned width `w` and height `h`, the ARM64 operations give `2/w`, `2/d`, float bits `0xb8000100`, `(-w)/w`, `(-h)/d`, and negative zero, respectively, where `d` is `0 - h` when the boolean is zero and `h` otherwise. The divisions and conversions execute in binary32; their order matters. The getter recomputes these values on each call rather than returning a cached matrix. The x/y origin does not directly enter this getter beyond the rectangle passed to the imported width/height methods. Zero sizes, integer overflow, alternative symbol bindings, and floating-point edge cases are not covered by the simplified expression.

This is a manually interpreted static path with selected instruction checks, not a complete dataflow proof or an actual page or Pencil2 runtime capture. The constructors and getter can be interposed; the external rectangle methods and caller-selected bitmap and boolean are not resolved here. In particular, these findings do not establish how a saved page selects its screen dimensions, orientation, canvas model matrix, or rendering schedule. The screen constructor queues render-target creation, so a constructor return alone does not establish that its target is ready. The same binary and toolchain qualifications above apply.

`python3 tools/pencil2-canvas-matrix/runtime-projection-probe.py` invokes the shipped ARM64 `SPScreenBitmap::GetProjectionMatrix` directly in the pinned synthetic list runtime after its successful 84-point dispatch. It supplies a fabricated bitmap rectangle `(3, 5, 195, 197)` and each boolean orientation, then checks all 16 returned float lanes bit for bit against the static expression, including negative zero. The [receipt](runtime-projection-receipt.json) records the resulting matrices and script identity. This direct call confirms the getter for those inputs in the emulated native runtime; the fabricated object does not run the constructor, and the list did not call this getter. It does not establish actual page scheduling or a renderer matrix handoff. The synthetic adapters and pinned dependency limitations in the [list probe](../pencil2-page-v219/README.md) apply.

`python3 tools/pencil2-canvas-matrix/runtime-canvas-product.py` explicitly hands the Matrix3 observed at the synthetic list's canvas calls to the shipped `SPPenCanvas::GetCanvasMatrix` after the list returns. It fabricates canvas and screen bitmap objects and vtables, uses the native screen writable accessor and projection thunk, and supplies the model matrix via a host virtual-method adapter. The complete native getter, projection getter and product helper execute in the emulated runtime. The [receipt](runtime-canvas-product-receipt.json) records both that list matrix and a separate nonuniform scale/shear/translation control; their returned products agree within 1e-6 with the column-major projection-times-expanded-model expression. The latter matrix is caller-supplied and was not observed in the list. This explicit handoff does not establish that a real page uses these dimensions, calls this getter, reaches RTV4 Draw with its result, or produces corresponding device pixels. The list probe's adapter and dependency limitations remain in force.
