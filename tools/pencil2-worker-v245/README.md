# Pencil2 render-message model matrix handoff

Run `python3 tools/pencil2-worker-v245/check.py` to check selected ARM64 instructions and relocations from the pinned shipped `libSPenPenCommon.so` and `libSPenPencil2.so`. It uses the project-local AArch64 binutils and `readelf`/`c++filt`. The check samples the dataflow and dispatch instructions; the description below also depends on manual interpretation of the surrounding disassembly.

In `PenReturnCallback`'s destructor, the nonempty-buffer path constructs a `PenGLRenderMsg` and invokes canvas virtual slot 216 at RVA `0x5053c`, storing the returned nine-float matrix in a 4×4 expansion at message offset 72. The existing [canvas check](../pencil2-canvas-matrix/README.md) resolves that slot to `GetModelMatrix` for the default `SPPenCanvas` and `SPPenCanvasRT` vtables. The callback then queues the message. The `PenGLRenderMsg` vtable's Run entry is RVA `0x4676c`; after its bitmap and intersection checks, RVA `0x4695c` passes the selected sub-bitmap and the message's 4×4 at offset 72 to the drawable's slot 104. The RTV4 vtable's slot 104 resolves to `Pencil2StrokeDrawableRTV4::Draw`. Thus, when this callback, these concrete default vtables, and this dispatch path are used, the Draw argument comes from the expanded model matrix, not the projection-times-model returned by `GetCanvasMatrix`. This explains why the [explicit product control](../pencil2-worker-v244/README.md) should not be interpreted as this callback's handoff.

This is static dataflow, not observation that the synthetic worker schedules or executes this render message. Overrides, symbol interposition, an alternate callback, bitmap and clipping conditions, normal scheduling, and saved-page or device execution remain unverified. The check does not prove every expansion instruction or all possible paths.
