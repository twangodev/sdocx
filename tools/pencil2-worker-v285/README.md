# Pencil2 queue PLT entry control

After the v219 preparation, run `python3 tools/pencil2-worker-v285/probe.py` and `PENCIL_SKIP_DRAW=1 python3 tools/pencil2-worker-v285/probe.py`. This extends v284 by allowing the three previously skipped native PLT entries at `0x9063fc0`, `0x9063fe0`, and `0x9063fb0` to execute. An entry hook asserts that both critical-section constructor and destructor PLT entries are reached. Both runs retain the v284 assertions for the constructor task, FIFO submission and drain, native canvas and framebuffer, and draw/skip outputs. The draw changes 322 bytes and the skip changes none.

This only removes the direct entry skips. The inherited harness still stubs pthread mutex operations, and the compare-and-swap and pointer exchange remain host adapters. Thus this is not evidence of real locking, concurrency, native teardown or resource lifetime. It retains the other v284 limitations, including single-threaded ARM64 emulation, host Mesa, and no original saved-page traversal or device parity. See the v284 README for the environment and intervention details.

The pinned `libSPenRenderer.so` SHA-256 is `f38df5db5e64f80c0641b6cee980e14533bd78e8e6eb34f250bd703d28119aed`. The emulator loads it at `0x9000000`, so the three entries correspond to ELF offsets `0x63fb0`, `0x63fc0`, and `0x63fe0`. Cross-objdump identifies these as PLT entries for `__android_log_print`, `SPen::AutoCriticalSection::AutoCriticalSection(SPen::CriticalSection*)`, and `SPen::AutoCriticalSection::~AutoCriticalSection()`, respectively. Each loads its branch target from the GOT and branches through `x17`; `readelf -rW` identifies `R_AARCH64_JUMP_SLOT` relocations at `0x6d9c0`, `0x6d9c8`, and `0x6d9d8` for those respective symbols. The entry assertion covers both critical-section PLT entries; it does not establish real mutex behavior.

In the same renderer, `AGLLThreadGLImpl::RunTasks` at ELF offset `0x4fac8` loads vtable slot 16 at `0x4faf8` and calls it at `0x4fafc`; the instruction at `0x4fb00` is the return site. It then loads slot 8 at `0x4fb08` and calls it at `0x4fb0c`; `0x4fb10` is the return site before the next dequeue. The probe asserts these sites in the emulated run, with the constructor task's slot-8 entry additionally observed. The return site alone does not identify what slot 8 did or prove resource destruction.
