# TapePen identity-matrix display controls

These synthetic native host-Mesa Drawing controls hold the input, identity matrix and 512×512 bitmap fixed while changing IDisplay from 256×256 to 512×512. The complete native RGBA frames differ by 15,115 absolute channel levels across 423 channels (maximum 131). The 256-display frame's 256×256 crop is byte-identical to the original v173 1× frame, which used a 256×256 bitmap. This establishes a display-profile effect in this control, without establishing its full cause or device or saved-document parity.

A source-generated v173 mask using the existing `tape_size_level` and `tape_aa_width` functions, exported through the existing pixel-grid vector diagnostic, reduces the 512-display crop's premultiplied RGBA L1 error from 15,132 with 256-display AA to 11,123 with 512-display AA, with respective maximum errors 131 and 113. The 512-display adjustment alone does not reproduce the native frame. These are SVG diagnostic measurements, not paired native PDF tests, and are insufficient to justify a production export profile. resvg 0.45.1 and Pillow premultiplication were used.

Both wrappers require the pinned local prerequisites described in `fixed-screen-2x-README.md`. Capture with `UV_CACHE_DIR=/tmp/sdocx-uv-cache uv run --offline --with unicorn==2.1.4 python tools/tapepen-public-drawing/identity-screen-256.py --run --shape64 --size12 > /tmp/tape-identity-256.log`, and repeat with `identity-screen-512.py`. Run the corresponding `verify-identity-screen-256.py` and `verify-identity-screen-512.py` with each log; they check input, native hashes, profile, framebuffer attachment, retained frame, and the reported frame difference. The wrappers assert native screen resolution calls during capture. The native verifiers retain `v173-1x-frame.rgba.zlib` as the original 1× reference. Export/intervention scaffolding has been retired; all reader measurements below and above are historical.

A fresh paired capture's [native uniform comparison](identity-screen-state-receipt.json) identifies two additional display-dependent inputs. At display 256 versus 512, `uVertexHalfExtent` changes from approximately (1.68, 6.72) to (1.77545, 7.10182), and `patternSize` changes from (64, 64) to (128, 128). `uEllipseRadii` remains (1.5, 6), `grainOffset` remains (77, 59), and the observed position and shadow offsets are unchanged. The earlier AA-only diagnostic held the quad extent and pattern size fixed, so it did not model these native state changes. Their presence explains why that approximation is incomplete; it does not quantify each contribution or prove the complete pattern/composite mapping. The separate `identity-screen-state.py` script checks both capture verifiers and hashes each native uniform payload before comparing them. The compact compressed capture logs are retained as `identity-screen-state-256.log.gz` and `identity-screen-state-512.log.gz`; decompress them to temporary paths and pass those paths to the script. The script pins those exact log hashes, checks ordered program uses, actual draw program, uniform locations and payloads, and records the selected provenance. A new capture has its own log identity and requires a separately reviewed receipt. No public export dispatch is warranted by this bounded state comparison.

A further source intervention regenerates the 512-display AA mask with both observed quad extents. The masks are byte-identical for this trajectory: changing the quad alone has no observable effect here. Using the captured shader's fragment-coordinate period of 128 instead of 64 in the diagnostic texture sampling reduces premultiplied RGBA L1 error against the 512-display crop from 11,123 to 5,303 (maximum channel error 113 to 73; differing channels 258 to 272). The period intervention samples at `(pixel + 0.5 - grainOffset) * 64 / 128 - 0.5`, retaining bilinear pixel-center semantics. This is a bounded diagnostic, not proof of the full material pipeline or a public rendering profile.

Fresh paired native captures passed the existing 256 and 512 verifiers; their full log SHA-256 values were `9cf68e04038c11d0d289446693e020c8a1f346980d798be589f3166a24e128bc` and `0c4ce11b9303f473f02a4f56b23e78164622ff09177075f3a688e8e82ba2ffc4`, respectively. A fresh public generic SVG and direct document PDF, were compared with their 256×256 native crops on white. Resvg RGB L1 was 70,165 and 72,480 for displays 256 and 512; MuPDF direct PDF RGB L1 was 70,043 and 72,378. Maximum RGB error was 204 in all four comparisons. These public fallback measurements and the diagnostic above have different alpha and white-background metrics and should not be ranked directly. The fresh log identities are recorded for provenance; the verifiers bind the captured frame and inputs, and the retained frames remain the reproducible oracle.

The retained 512-display upload log resolves the remaining large texture discrepancy: event 6 is a native `glTexSubImage2D` of a 128×128 RGBA8 image, with native-owned input bytes SHA-256 `f290e56addf62df35c7fbd4bfb6bddaeccc047ab382c52aa9766cafb38b7d292`. It is a texture upload, not framebuffer readback. The capture loads the pinned pattern 1 SVG before drawing. Sampling this captured image at `(x - 77, y - 59)` with the source-generated 512-display mask gives a pixel-grid SVG with premultiplied RGBA L1 28 and maximum error 1 against the native crop; its SVG-derived MuPDF PDF gives L1 453 and maximum error 2. These are diagnostic outputs, not a direct document PDF or a general source asset rasterizer. The previously measured public SVG and direct document PDF remain the generic fallback. This one synthetic host control does not justify a general rendering profile or device parity.

The historical source-asset control loaded the locally extracted APK `tape_pattern_01.svg` only if its SHA-256 is `9f8b208a01db838235f795226acd6e68aa42e609b06c6e171a29447f8b68322b`. The capture passes those bytes to native `SetTapePenPatternSvgUtf8Bytes(1, ...)`. The pinned TapePen library exports `SPen::RasterizeTapePenPatternFromSvg`, `nsvgParse`, and `nsvgRasterize`; the same capture records 540 parser `pow` calls and 136 `acosf` calls at pinned sites in that rasterization path. The 128×128 upload and its allocation are separately captured. This supports the source-to-upload route, although the log does not trace every byte through each intermediate. Rendering the packaged SVG at 128×128 with resvg 0.45.1 gives a texture whose RGBA L1 difference from the native upload is 58,560, maximum 33, across 3,072 channels. Feeding that source-generated image into the diagnostic gives SVG L1 612, maximum 25, and SVG-derived MuPDF L1 1,036, maximum 25. The source control required the locally extracted APK asset.

The shipped AArch64 library exports the NanoSVG entry points, but no NanoSVG source or headers were found in the local system includes or Cargo registry. A Rust implementation would need to reproduce the native parser, geometry/rasterizer, antialiasing and color conversion, as well as its dimensions and host math behavior; matching the two image sizes and changed SVG inputs against native uploads is needed before generalizing. The source-derived image is an approximation, and neither diagnostic PDF is a public direct document PDF.
