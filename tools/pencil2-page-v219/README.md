# Synthetic Pencil2 object-list probe

From the repository root, check the existing adapter's 33 pinned dependencies and run both captures:

```sh
python3 tools/pencil2-page-v219/prepare.py
python3 -c "import importlib.util; p='tools/pencil2-page-v219/native/tmp/vector-parity-plan/pen-family-audit/pencil2-v14-geometry-v12/capture_candidate.py'; s=importlib.util.spec_from_file_location('capture',p); m=importlib.util.module_from_spec(s); s.loader.exec_module(m); m.check_pins()"
python3 tools/pencil2-page-v219/probe.py
python3 tools/pencil2-page-v219/queue-probe.py
```

The scripts hash-check that adapter (SHA-256 `996ef6db3a376619e9e5d1d05b7d5e1a940726f3feb2ef6895275a705576ee3e`). The adapter and source helpers are preserved under `native/tmp`, with their original bytes and directory relationships. `prepare.py` restores the baseline's exact pinned bytes from the shared `tools/pencil2-drawing-capture-closure/sources/v10_baseline_capture.json.gz` without replacing different existing data. It also creates untracked relative `scratch` links that point to the existing project runtime and native DSOs; those binaries are not copied. `dependencies.json` records the paths at the original capture and their pinned hashes; the preserved source paths now live under `native/tmp`. The first command and both probe scripts check all pins, including native DSOs, Unicorn, ARM binutils, host tools and the Python interpreter. The runtime dependencies remain local and this is not a clean-checkout reproduction. The receipts retain the original probe hashes from the original capture; subsequent probe changes select the preserved adapter path and verify all dependency pins. Both probes were rerun successfully with the preserved inputs. Run without Python optimization; all three capture entrypoints reject `-O`. The preserved bridge still requires this checkout at `/home/jding/RustroverProjects/sdocx`.

The first probe records an expected queue-sentinel failure after native Pencil2 V14 redraw and 84 AddPoint calls. The second uses an explicit synthetic context-query intervention at three observed Drawing call sites and returns successfully. It verifies ordered native list dispatch and two exact canvas matrix arguments for a caller-supplied matrix. Both runs use one synthetic object and host bitmap, canvas, context, task queue, renderer holder, loader and allocator adapters. Neither establishes real document page traversal, native GPU output, pixels or device parity. See the separate receipts for each outcome.

`python3 tools/pencil2-page-v219/mesa-merge.py` combines the list adapter with the existing Mesa bridge. It checks the adapter dependencies and hashes the queue adapter, Mesa bridge, Mesa helper and Renderer DSO before execution. The native list dispatch and supplied Matrix3 arguments are asserted, followed by the existing explicit saved-redraw replay and an explicit RTV4 Draw using a separately supplied Matrix4. The list-selected RTV4 address is checked against the explicit draw address. A transparent 192×192 host Mesa target produced 317 nonzero RGBA bytes with zero recorded GL error; the compact [receipt](mesa-receipt.json) records the framebuffer hash and inputs. Framebuffer, generated harness and capture files live in one owned temporary directory, which is removed on success or failure. The script checks the reported capture path before reading it. The receipt records the merge script hash. This is a synthetic manual handoff, not evidence that list return automatically painted, that the two matrices are related as on a real page, or that a saved document or device matches. Host EGL, GLES, Mesa drivers and their transitive shared libraries are not pinned; the receipt describes this host runtime only.

`python3 tools/pencil2-page-v219/no-replay.py` moves that same explicit Mesa initialization, update and draw to immediately before the saved-redraw call, then exits before replay. On the tested host, the list-selected RTV4 updates 84 records and produces 317 nonzero framebuffer bytes with GL error zero; its readback hash matches the prior replay control. The [receipt](no-replay-receipt.json) records the input matrices and boundaries. This shows the synthetic list-generated renderer state can feed the manually invoked GPU path without the second redraw. It does not establish automatic list painting or a relationship between the independently supplied matrices; the host adapters and unpinned Mesa dependencies above still apply.

`python3 tools/pencil2-page-v219/lifecycle-probe.py` adds entry-point tracing to the pinned queue probe. During its synchronous list call, all three RTV4 symbols (Init, Update and Draw) resolve, but none is entered; the list still returns successfully, forwards the supplied Matrix3 twice and issues 84 AddPoint calls. The [receipt](lifecycle-receipt.json) records the bounded observation. The synthetic task and context adapters can affect scheduling, so this does not establish a real page lifecycle or a Matrix3-to-Matrix4 conversion.

`python3 tools/pencil2-page-v219/dispatch-probe.py` traces the synthetic synchronous queue adapter during the list call. Six task entries occur; their stored member pointers identify `PenDrawableRT::SetRedrawState`, `SetPenData`, `Pencil2StrokeDrawableRTV4::SetStartPoint`, `PenDrawableRT::SetRect`, and `PenStrokeDataManager::ReleaseStrokeData`. The sixth task uses an `IContextHolder` member pointer encoded as `0x28`; the holder is a stub. The [receipt](dispatch-receipt.json) retains task objects and method pointers. These are native-created tasks run by the adapter, not evidence of the real application's queue ordering. None identifies renderer Init, Update, or Draw; the reason actual page painting is not reached remains unresolved.

`python3 tools/pencil2-page-v219/multi-matrix-probe.py` inserts the same synthetic object pointer twice into the native list and repeats the call with the original matrix and a nonuniform-scale/shear matrix. In each case, both list entries follow the observed GetData/drawObject/drawObjectStroke/RedrawPen sequence, producing 168 AddPoint calls; the two canvas matrix calls receive the supplied matrix exactly. The [receipt](multi-matrix-receipt.json) records both runs. This extends list and matrix forwarding evidence only: the entries are not distinct objects, and the synthetic synchronous queue, context interventions and canvas adapters do not establish automatic GPU paint, a Matrix3-to-Matrix4 conversion, saved-page traversal or device behavior.

`python3 tools/pencil2-page-v219/distinct-matrix-probe.py` constructs a second ObjectStroke and ObjectStrokeImpl, uses native Copy for its stroke content, and constructs its visible base. The two distinct object pointers both reach RedrawPen in list order with 168 total AddPoint calls for each matrix, and both canvas matrix calls receive the caller's matrix. The [receipt](distinct-matrix-receipt.json) retains the two observations. The copied strokes have the same content; this does not establish varied-object output, automatic painting, the Matrix4 conversion, or saved-page scheduling.

`python3 tools/pencil2-page-v219/canvas-entry-probe.py` traces both Graphics `SPPenCanvas::GetCanvasMatrix` and `SPPenCanvasRT::GetCanvasMatrix` entry points during the same synthetic synchronous list call. Neither is entered, while the call forwards the supplied Matrix3 twice and issues 84 AddPoint calls; the [receipt](canvas-entry-receipt.json) records the resolved symbols and observations. The host adapters and context interventions limit this result to the probe; it does not establish real-page scheduling or a Matrix3-to-Matrix4 handoff.

`validation.json` describes a historical rerun; its `prepare.py` hash predates the shared archive-path change.
